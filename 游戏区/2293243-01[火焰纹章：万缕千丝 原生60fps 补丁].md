补丁只改运行时的一个整数字段，不含任何游戏文件、密钥或破解内容，仅供研究交流。

仓库（双语说明、安装、排错、FPSLocker格式）：
[https://github.com/weile10000/FEFW-60fps](https://github.com/weile10000/FEFW-60fps)（想研究的可以去看看）

这游戏锁30帧，IS在程序内偷偷存了个"目标帧率"字段（菜单60、战斗30）。

把这个字段写死60，游戏就会自己按60帧出画面，而且——重点——速度不变。

补丁本体是4行金手指，装上即用，不加速、不插帧、不吃配置。

Ctrl+U那套是邪道：

不少人发现Ctrl+U（解除限速）能跑到60-90帧，看着很爽。

但本作的逻辑是跟"每一帧"绑定的，解除限速=游戏整体2-3倍速：

角色走路像踩了风火轮，动画像开了1.5倍速播放，战斗节奏全乱。

这不是60帧，这是快进。

这游戏的时间是怎么算的：这也是折腾研究的乐趣

用一句话概括：游戏内部有个"目标帧率"target（菜单里是60，进战斗改成30），

然后有59处代码在按 60.0 / target 换算逻辑步进。

target=30 → 每帧走2.0；target=60 → 每帧走1.0。

所以只要把target写死成60，帧数翻倍、步进减半，时间流速纹丝不动。

IS官方自己留的后门，也许将来有官方原生60FPS？。

怎么发现的（给同样想折腾的朋友）

1. 先在模拟器里挂GDB，断在present调用点，拿到游戏侧的调用栈（main+0x64995c）；

2. 顺着渲染任务找到present interval的计算逻辑，发现它读一个全局对象里的 +0x1dc；

3. 关键是去翻了 Mac 原生移植项目 nxnative 的 per-game 文档——人家已经把本作的

   图形对象结构（+0x1d8 显示率 / +0x1dc 目标帧率 / +0x1e0 最长间隔）和

   "59处按60/target步进"写得很明白，互相验证了，属于站在巨人肩膀上摘桃子，这下真的only apple can do（doge）

4. 运行时把 +0x1dc 写成60，日志里 present interval 立刻从2变1，主循环频率翻倍，实锤。

【补丁长什么样】

Eden/Eglantine 的金手指，四行：

[60fps]

40010000 00000000 0000003C

58000000 021E60D8

98000100 00000000 000001DC

A4100200 00000000

翻译成人话：R1=60；R0=读[main+0x21E60D8]；R0+=0x1DC；把R1写进[R0]。

每帧执行一次，就这么简单。

想自己动手的：

安装（Windows / Eglantine）

1. 先启动一次游戏，打开 %APPDATA%\eden\log\eden_log.txt，

   搜 "build_id="，会看到类似 No cheats file found ... build_id=DB93B0125F485060

   这16位十六进制就是你的build id；

2. 把补丁文件改名为 &lt;build id&gt;.txt，放到：

   %APPDATA%\eden\load\04007EF01F8AE000\60fps\cheats\

3. 重启模拟器，进游戏看右下角。

   日志里出现 present #1 swap interval 1 (word 12 = 0x1003c) 就是生效了。

注意：金手指文件里千万别写#注释，这模拟器的解析器只认[名字]和十六进制，

多一个#整份文件直接静默失效（我在这上面浪费了一晚上）。

【实测】

5600X + 6800XT，1.5X分辨率、VSync关、VRR开：

· 战斗场景 16.7ms/帧，稳60；

· 战术界面/人多时 28-37ms，掉到30-40帧；

· 把GPU模式调成"高速"、围栏行为"默认"、关掉同步内存操作后，fence从20ms降到11ms，

  实际能到50-60，VRR下很顺。

注意"GPU模式=高速"可能有贴图/特效异常，遇到就退回"精确"，靠VRR吃40-50帧。

【已知问题】

· PGO/MinGW 构建播不了过场（CG被跳过），换MSVC标准构建即可，这是模拟器老问题；

· 某些场景会有贴图格式断言（format_lookup_table.cpp:278），不致命，模拟器继续跑；

· 游戏更新后偏移会变，需要重新定位（方法我写在仓库README里了）。

省事的话把下面这段发给AI让他帮你，自己调有点麻烦。

用 main 那一行的前 16 位

你的日志里每个模块都有自己的 build id：

模块        完整 build id        用途

rtld        0EAD38AD96DAD995…        加载器

main        DB93B0125F4850601D61C3EDDE012F8EB2ECFE77        游戏本体 ← 用这个

subsdk0        3ADF85C89D764277…        DLSS（未加载）

subsdk1        45EAC7636FFC32C7…        CUDA（未加载）

subsdk2        7D73F8E808341683…        影片

sdk        5B1602F3A2965F44…        系统库

金手指按模块归属：文件名的 build id 决定这条 cheat 相对哪个模块的基址生效。

我们的补丁地址是 MAIN + 0x21E60D8，必须挂在 main 上，所以文件名取 main 的前 16 位：

代码块

DB93B0125F485060.txt

路径：

代码块

%APPDATA%\eden\load\04007EF01F8AE000\60fps\cheats\DB93B0125F485060.txt

两个容易混的点

16 位 vs 40 位：日志里 HasNSOPatch ... build_id=DB93B0125F4850601D61C3EDDE012F8EB2ECFE77 是 40 位的完整 id（用于查 NSO patch/mod），而金手指查找用的是前 16 位（No cheats file found ... build_id=DB93B0125F485060）。文件名用 16 位。

别用 sdk 或 subsdk 的 id：挂错模块，地址会按那个模块的基址计算，写到的就是错误内存——轻则无效，重则崩溃。

你启动游戏后搜日志里的：

代码块

No cheats file found for title_id=04007EF01F8AE000, build_id=XXXXXXXX

里面出现的 16 位 id 就是你要用的（会有多个，对应不同模块），挑和 Module main loaded 同一时刻、且名字是 main 的那条。

如果你的 main id 不是 DB93B0125F485060（比如游戏更新到别的版本），那说明是另一个版本，偏移需要重新定位。
